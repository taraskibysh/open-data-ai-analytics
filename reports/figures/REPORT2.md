# ЗВІТ З ЛАБОРАТОРНОЇ РОБОТИ
**Тема:** Побудова CI-конвеєра із використанням GitHub Actions  
**Мета:** Налаштувати CI для автоматичного запуску модульних задач (завантаження даних, аналітика, візуалізація, тести) при подіях push/pull_request; налаштувати CD для публікації звітів на GitHub Pages; підключити та протестувати локального агента (self-hosted runner).

---

## Частина А. Налаштування CI-конвеєра (GitHub-hosted)

Для автоматизації перевірки коду було створено конфігураційний файл `.github/workflows/ci.yaml`. 

**Основні налаштування та архітектура:**
* **Тригери (Events):** Пайплайн налаштовано на автоматичний запуск при подіях `push` та `pull_request` у гілку `main`. Також реалізовано ручний запуск (`workflow_dispatch`) із можливістю вибору конкретного модуля через випадаючий список.
* **Матрична стратегія (Matrix Strategy):** Використано `strategy.matrix` для паралельного виконання незалежних ізольованих середовищ для чотирьох модулів: `data_loader`, `data_research`, `visualization` та `tests`.
* **Збереження артефактів:** Результати виконання (HTML-звіти, лог-файли) автоматично збережено за допомогою екшену `actions/upload-artifact@v4`.

---

## Частина B. CD та публікація результатів

Реалізовано Варіант 2 — автоматичну публікацію результатів візуалізації у GitHub Pages.

**Процес деплою:**
1. На віртуальній машині послідовно запускаються скрипти: завантаження сирих даних (`data_loader.py`), їх кластеризація та проміжна обробка (`data_research.ipynb`), і врешті-решт — побудова фінальних графіків (`visualization.ipynb`).
2. Отриманий HTML-звіт зберігається як спеціальний артефакт.
3. Створено окрему job `deploy-pages`, яка використовує середовище `github-pages`. 
4. **Умова безпеки:** Деплой налаштовано таким чином, щоб він відбувався **тільки** при автоматичному `push` у гілку `main`. При ручному тестуванні (`workflow_dispatch`) або під час перевірки `pull_request` цей крок автоматично пропускається, щоб уникнути публікації неперевірених даних.

---

## Частина C. Налаштування локального агента (Self-hosted runner)

Для перевірки роботи пайплайну поза межами хмари GitHub, було розгорнуто локального агента на базі підсистеми WSL2 (Ubuntu).

**Процес налаштування:**
1. Завантажено та налаштовано агент виконання через скрипти `./config.sh` та `./run.sh`.
2. Створено окремий файл `.github/workflows/ci-selfhosted.yaml`. Оскільки локальний ПК не використовує хмарний кеш, крок `actions/setup-python` було замінено на створення класичного віртуального середовища (`python -m venv venv`) для ізоляції залежностей.

### Порівняльний аналіз: GitHub-hosted vs Self-hosted runners

| Критерій | GitHub-hosted Runner (`ubuntu-latest`) | Self-hosted Runner (Локальний ПК/WSL) |
| :--- | :--- | :--- |
| **Швидкість** | Витрачає час на "прогрів": виділення нової ВМ, завантаження ОС, встановлення Python та завантаження бібліотек "з нуля" при кожному запуску. | Запуск відбувається майже миттєво. Завдяки наявності постійного локального `venv`, час на встановлення бібліотек (`pip install`) зводиться до мінімуму. |
| **Доступ до ресурсів** | Суворо ізольоване середовище. Дані потрібно завантажувати через інтернет. Немає доступу до локальних баз даних. | Має прямий доступ до жорсткого диска. Дозволяє обробляти великі датасети локально та звертатися до закритих корпоративних ресурсів (БД, VPN). |
| **Безпека (Ризики)** | Високий рівень безпеки. Код виконується на ізольованій машині, яка знищується після роботи. | **Ризик для безпеки.** Шкідливий код у Pull Request може отримати доступ до особистих файлів на комп'ютері. Використовується переважно у приватних репозиторіях. |

## Висновки
У ході лабораторної роботи було успішно побудовано повноцінний CI/CD конвеєр. Налаштовано паралельне тестування ізольованих модулів за допомогою матричної стратегії, реалізовано фільтрацію за зміненими файлами для економії ресурсів, та налаштовано автоматичний деплой результатів аналітики на GitHub Pages. На практиці досліджено процес підключення локального агента виконання (self-hosted runner) та проаналізовано його переваги й недоліки в порівнянні з хмарними рішеннями.
